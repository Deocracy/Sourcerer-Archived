<objective>
Define the substrate once (D-15), expose it as both the real WSL image target and a plain-VM
variant, and wire the plain-VM variant into a `nix flake check` boot test that asserts the VM
reaches multi-user and a service inside it answers on loopback (D-12).

Purpose: this is the "seed nixosTest" leg of FOUND-02 and the buildable closure FOUND-01's
cache-only build will target. It is deliberately a working miniature of Phase 13's real check
(the Databasise engine answering on loopback) — the plumbing is proven in the exact shape it
gets reused.
Output: three substrate modules, one nixosTest, and the flake outputs that expose them.
</objective>

  </read_first>
  <action>
    Create `nix/substrate/core.nix` as an ordinary NixOS module (`{ pkgs, ... }: { ... }`). This
    file is the single definition of what the substrate contains; both variants import it and
    neither adds contents of its own beyond its adapter layer.

    Contents:
    - A normal user named `sourcerer` (`isNormalUser = true`, `extraGroups = [ "wheel" ]`). This
      is the account the WSL variant will set as the default user; it is nothing user-facing in
      the product sense, it is the shell the substrate runs work under.
    - `nix.settings.experimental-features = [ "nix-command" "flakes" ]` and
      `nix.settings.trusted-users = [ "root" "sourcerer" ]` — the substrate is Nix-native by the
      project's standing rule, so flakes must work inside it from first boot.
    - `programs.nix-ld.enable = true`, with `programs.nix-ld.libraries` extended with
      `pkgs.stdenv.cc.cc.lib`, `pkgs.zlib`, `pkgs.openssl`. **This is the vscode-server support
      D-14 asks for**: VS Code Remote downloads its own dynamically-linked glibc server binaries
      into `~/.vscode-server`, and nix-ld is the loader shim that lets them run on NixOS. Do NOT
      add a `nix-community/nixos-vscode-server` flake input — that project is the pre-nix-ld
      workaround and `services.vscode-server` does not exist in nixpkgs 26.05. Put a comment in
      the file stating this, so the next reader does not re-add the input.
    - `system.stateVersion = "26.05"` — set here so both variants inherit one value.
    - The D-12 seed placeholder service. Define a docroot with
      `pkgs.writeTextDir "index.html" "sourcerer-substrate-seed-ok\n"` and a
      `systemd.services.seed-placeholder` that is `wantedBy = [ "multi-user.target" ]` and runs
      `python3Minimal -m http.server 8080 --bind 127.0.0.1 --directory <that docroot>`.
      Bind to `127.0.0.1` and never `0.0.0.0` — this placeholder is the shape later phases copy,
      and a `0.0.0.0` bind here would propagate as a bad precedent. Use `python3Minimal`, not
      full `python3`, to keep the placeholder's weight off the substrate closure.
      Add a comment naming it as the seed stand-in that Phase 13's real engine health check
      replaces.

    Explicitly do NOT add: any systemd hardening directives (`ProtectSystem`,
    `RestrictNamespaces`, `SystemCallFilter`, `CapabilityBoundingSet`, `DynamicUser`, …) to the
    seed service or anywhere else. D-14 is explicit that with Phase 8 deferred there is no
    measured exemption set, so authoring an app-unit hardening template now would encode
    guesses; Phase 15 owns it. Do NOT add `services.openssh`, a desktop environment, firewall
    rules, or any WSL-specific option — WSL options belong only in the WSL variant.
  </action>

  <action>
    Create `nix/checks/seed-boot-test.nix` as a function taking `{ pkgs, vmModule }` and returning
    `pkgs.testers.runNixOSTest { ... }` (the current API on nixpkgs 26.05; `pkgs.nixosTest` is the
    older spelling — prefer `testers.runNixOSTest`).

    Test definition:
    - `name = "seed-boot-test"`.
    - `nodes.machine = { imports = [ vmModule ]; }` — the plain-VM variant, never the WSL one.
    - `testScript` performing, in order:
      `machine.wait_for_unit("multi-user.target")` — D-12's "boots" assertion;
      `machine.wait_for_unit("seed-placeholder.service")`;
      `machine.wait_for_open_port(8080)`;
      then capture the response with
      `machine.succeed("curl -sf http://127.0.0.1:8080/")` and assert the returned body contains
      `sourcerer-substrate-seed-ok`. Asserting the body, not merely a 200, is what makes this a
      real service-answers check rather than a port-is-listening check — that distinction is the
      whole point of D-12 and is the shape Phase 13 reuses for the engine.
      Also assert `machine.succeed("nix --version")` so the substrate's Nix-native premise is
      checked at boot rather than assumed.
    - Ensure `curl` is available inside the test VM (add `environment.systemPackages` with
      `pkgs.curl` in the test's node definition, not in `core.nix` — the substrate itself should
      not carry a package only the test needs).

    Wire it into `flake.nix` as `checks.x86_64-linux.seed-boot-test`, importing the file with
    `pkgs` and `vmModule = ./nix/substrate/vm-variant.nix`. Placing it under `checks` is what
    makes `nix flake check` build and run it automatically — that is the mechanism Plan 04's CI
    job depends on, so do not expose it only as a `package`.

    Then run `nix flake check` locally on the dev host and get it green. This build boots a QEMU
    VM and takes minutes; that is expected. Do not add `--no-build`, which would skip the very
    thing this task exists to prove.
  </action>
