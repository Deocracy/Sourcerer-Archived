  <action>
    Add a top-level `nixConfig` attribute to `flake.nix` with
    `extra-substituters = [ "https://<cache-hostname>/sourcerer" ]` and
    `extra-trusted-public-keys = [ "<the cache's public signing key, verbatim>" ]`, using the
    exact hostname and key recorded in Plan 05's summary. Copy the key character for character —
    a single wrong character produces signature-verification failures that read like network
    errors and waste hours.

    Put the substituter in the flake rather than documenting an `attic use` setup step, because
    FOUND-01's claim is specifically about a *fresh clone* on a second machine: with `nixConfig`
    the very first `nix build` in that clone already knows where to fetch from. Add a comment
    above the block stating that Nix prompts once to accept a flake's `nixConfig` (or requires
    `--accept-flake-config`, or the user being in `trusted-users`), so the first-run behavior is
    not a surprise on the second machine.

    Add a second comment recording that the cache is a plain substituter URL and therefore
    swappable by construction — replacing this one line is the entire migration path if Attic or
    AWS ever has to be abandoned. That is the property D-01 was chosen for, and it should be
    visible where the coupling actually lives.

    Do not add the cache to `nix.settings` in any of the substrate modules — the substrate's own
    substituter configuration is Phase 11's update-channel concern, and adding it here would
    quietly bake a production endpoint into the shipped image ahead of that decision.
  </action>

  <files>.github/workflows/ci.yml</files>
  <read_first>

    - .planning/phases/09-flake-foundation-assurance-chain/09-05-SUMMARY.md (the cache name, hostname, and the fact that `ATTIC_PUSH_TOKEN` is already set as a repository secret)
    - .planning/phases/09-flake-foundation-assurance-chain/09-CONTEXT.md (D-03 — the cache push IS the publish step until Phase 11)
    - .planning/phases/09-flake-foundation-assurance-chain/09-RESEARCH.md (Pattern 5 — `attic login` / `attic push` invocation shape)
  </read_first>
  <action>
    Add a `publish` job to `.github/workflows/ci.yml` on `ubuntu-latest`.

    Gating — this is the requirement, not a detail:
    - `needs: [nix-checks, windows-tauri]`. Because the drift gate runs as a step inside both of
      those jobs, a drift failure already turns its job red and therefore blocks this one.
    - `if: success() && github.event_name == 'push' && github.ref == 'refs/heads/<default branch>'`
      using the default branch Plan 04 actually settled on. Restricting to push-on-default means a
      pull request from a fork can never reach the push token.
    - `permissions: contents: read` only. This job needs no write access to the repository.

    Steps: `actions/checkout@v7`; `DeterminateSystems/nix-installer-action@v22`;
    `nix build .#substrate-system` (the closure, not the tarball builder — the tarball builder
    needs root to run, while its inputs are already inside this closure);
    then `attic login` against the cache hostname using `${{ secrets.ATTIC_PUSH_TOKEN }}`, then
    `attic push sourcerer ./result`.

    Use the token only through the `secrets` context. Do not `echo` it, do not write it to a file
    the workflow later cats, and do not pass it as a positional argument in a step that has
    `set -x` enabled — GitHub masks known secret values in logs, but a transformed or partially
    printed token defeats the mask.

    Add a comment in the job stating plainly that this push is the publish step for the whole
    project until Phase 11 builds the real update channel, and that its `needs:` list is what
    makes "a red CI run blocks any publish" (FOUND-02) literally true rather than a policy
    statement. If a future check is added to this workflow, it must be added to this list too.

    Push and confirm the job runs and succeeds on the default branch. Then confirm the closure
    actually landed: query the cache for one of the pushed store paths.
  </action>
  <verify>
    <automated>bash -c '
set -euo pipefail
grep -q "needs: \[nix-checks, windows-tauri\]" .github/workflows/ci.yml || grep -qE "needs:" .github/workflows/ci.yml
python3 - <<PY
import re,sys
w=open(".github/workflows/ci.yml").read()
assert "publish" in w, "no publish job"
assert "secrets.ATTIC_PUSH_TOKEN" in w, "token not referenced via secrets context"
assert "attic push" in w, "no attic push step"
assert "nix-checks" in w and "windows-tauri" in w, "publish not gated on both check jobs"
assert "pull_request" not in w.split("publish:")[1][:800] or "github.event_name == \x27push\x27" in w, "publish must be push-only"
print("workflow shape OK")
PY
gh run list --limit 1 --json conclusion --jq ".[0].conclusion" | grep -q success
gh run view --json jobs --jq "[.jobs[].name]" | tee /dev/stderr | grep -q publish
OUT=$(nix build .#substrate-system --no-link --print-out-paths)
HOST=$(grep -oP "(?<=https://)[^/\"]+" flake.nix | head -1)
HASH=$(basename "$OUT" | cut -d- -f1)
curl -sf "https://$HOST/sourcerer/$HASH.narinfo" > /dev/null
echo "publish gate OK — closure present in cache"
'</automated>
  </verify>
  <acceptance_criteria>
    - `.github/workflows/ci.yml` contains a `publish` job whose `needs:` lists both `nix-checks` and `windows-tauri`.
    - The job's `if:` restricts it to `push` events on the default branch — a `pull_request` event can never run it.
    - The job declares `permissions: contents: read`.
    - The push token is referenced only as `${{ secrets.ATTIC_PUSH_TOKEN }}` and never echoed, written to a file, or interpolated into a `set -x` command.
    - The latest run on the default branch shows a `publish` job with conclusion `success`.
    - `curl https://<cache-host>/sourcerer/<store-hash>.narinfo` for the `substrate-system` output path returns 200 — the closure is genuinely in the cache, not just reported as pushed.
    - A comment in the job states that this push is the publish step and that its `needs:` list is what enforces FOUND-02.
  </acceptance_criteria>
  <done>The substrate closure reaches the cache only through a job that cannot start until every check has passed.</done>

  <action>
    Create `docs/CACHE-RUNBOOK.md`. Match README.md's register: concrete, provenance-stamped,
    explicit about what does not exist yet. No aspirational prose, no "we will eventually"
    sections. Every command in it must be one someone can paste.

    Required sections:

    **Inventory.** Every resource Plan 05 created, by identifier: region, S3 bucket, IAM role and
    instance profile, security group id, key pair, instance id and type, Elastic IP, DNS record,
    cache name, and the cache's public signing key. This is the section that makes the rest
    actionable. The push token is deliberately absent — record only that it lives in the
    `ATTIC_PUSH_TOKEN` repository secret and how to re-mint it.

    **nixpkgs bump cadence (D-08).** The pin is `nixos-26.05`. Minor bumps within 26.05 are
    routine: `nix flake update nixpkgs`, push, let CI judge it. The 26.11 migration is a planned
    event, not a routine bump. State the interval you are committing to and what triggers an
    off-cadence bump (a security advisory affecting the substrate closure).

    **Red-channel response.** What to do when a bump turns CI red: the lock file is the pin, so
    reverting `flake.lock` reverts the world; the publish job's `needs:` gating means a red
    channel has already failed closed and nothing reached the cache. Give the exact revert
    command and say how to tell a genuine upstream breakage from a flaky nixosTest run.

    **Retention and GC (D-02).** The configured interval and retention period, where they are
    declared (`nix/attic/cache-host.nix`), and the verification command
    (`attic cache info sourcerer` showing nonzero retention). State Pitfall 5 explicitly: `0`
    disables GC rather than making it aggressive, so an apparently harmless edit to that line
    silently breaks this. Record the Attic-GC-vs-S3-lifecycle answer from Plan 05 and, if an S3
    lifecycle rule was needed, name it here.

    **Restore from scratch.** The ordered procedure to rebuild the cache after total loss:
    re-provision (or re-point) the instance, deploy with
    `nixos-rebuild switch --flake .#attic-cache --target-host ...`, recreate the cache, re-mint
    the CI token, and — the part that is easy to forget — note that the cache's **signing key
    changes**, so `flake.nix`'s `extra-trusted-public-keys` must be updated and every consumer
    re-accepts it. Also state that a lost cache is a rebuild, not a data loss: everything in it
    is reproducible from the flake, which is the whole reason a binary cache is safe to treat as
    disposable infrastructure.

    **Cost basis.** Real figures for the instance size, S3 storage and request charges, and data
    egress, stated against Deocracy's actual account terms — whether nonprofit credits/discounts
    are active, per Plan 05's checkpoint answer. D-01 chose AWS on the nonprofit-program math, so
    cite that basis rather than list price. If a figure could not be confirmed, say so plainly
    instead of estimating.

    **Known caveats.** Three, each in one short paragraph:
    (1) The seed nixosTest boots a plain QEMU VM, not WSL — it proves the substrate's *contents*,
    not the WSL adapter layer; a real-WSL smoke test is Phase 10's concern (RESEARCH Pitfall 1).
    (2) CI's Nix is **Determinate Nix**, not upstream, because `nix-installer-action` removed the
    upstream install path on 2026-01-01. This satisfies the project's "pin which Nix ships"
    decision for CI and should not be a surprise in a future debugging session (Pitfall 2).
    (3) Attic's crate carries a "WIP" label upstream. Pin the deployed `services.atticd` version
    and check Attic's changelog before letting a nixpkgs bump upgrade it blind (Pitfall 3). This
    is a maturity note, not a reason to revisit D-01.

    Do not restate the decision rationale for Attic-vs-Cachix or AWS-vs-Hetzner — that is settled
    in `09-CONTEXT.md` and repeating it here invites re-litigation.
