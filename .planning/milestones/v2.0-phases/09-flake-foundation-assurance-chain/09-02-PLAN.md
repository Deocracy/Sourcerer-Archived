    - `devShells.x86_64-linux.default` — the one shell for both worlds (D-16). Its packages:

      `nixos-rebuild`; `git`. Its Tauri Linux build inputs: `webkitgtk_4_1`, `libsoup_3`,
      `gtk3`, `librsvg`, `glib-networking`, `openssl`. Its native build inputs: `pkg-config`,
      `wrapGAppsHook4`. Use `webkitgtk_4_1` and `libsoup_3` — the soup2/`webkitgtk` 4.0
      attributes are the pre-Tauri-2 generation and will fail with missing
      `javascriptcoregtk-4.1`.
      Add a `shellHook` that exports `PKG_CONFIG_PATH` if needed for the `*-sys` crates and

      the shell is self-evidencing.
    - `lib` — `import ./nix/lib.nix { inherit nixpkgs; }` (D-09).
    - `overlays.default` — a named, deliberately near-empty overlay (`final: prev: { }`) with a
      comment stating that Phase 15's app compiler and Phase 16's submission format fill it,
      and that its existence today is what makes downstream app expressions evaluate against a
      surface that already exists.

    Author `nix/lib.nix` as the D-09 public surface. It takes `{ nixpkgs }` and returns an
    attrset with exactly three things and a header comment explaining each:
    - `pinnedNixpkgs = nixpkgs` — the re-export, so a downstream repo consuming this flake as a
      pinned input gets the identical nixpkgs revision by construction rather than by
      convention. This is what makes TOOLS-02 ("floating-ref installs impossible") mechanically
      true later.
    - `pkgsFor = system: import nixpkgs { inherit system; overlays = [ ]; }` — the single
      entry point downstream expressions use to get a package set from the pin.
    - `appModules = { }` — the deliberately empty slot. Comment it as the per-version-addressable
      app registry point (Phase 15/16) and the user-config import point named in the phase's
      direction of record. Do NOT invent a schema for it now; an empty attrset with a comment is
      the whole deliverable.
    Keep `nix/lib.nix` genuinely near-empty. Adding speculative helpers here is exactly the
    over-building D-09 was worded to prevent.

    Author `.envrc` containing `use flake` plus `watch_file rust-toolchain.toml` and
    `watch_file .nvmrc`, so direnv re-enters the shell when a pin changes. Do not commit
    `.envrc.local` or any direnv allow-state — `.direnv/` is already ignored by Plan 01.

    Then run `nix flake lock` (or `nix flake update`) to generate `flake.lock`, and COMMIT the
    lock. The branch name in an input URL is only where updates come from; `flake.lock` is the
    actual pin and FOUND-01's reproducibility claim rests entirely on it being committed.

    Finally run `nix flake check` — with no `checks` output yet it only evaluates the flake, which
    is precisely the gate that must pass before Plan 03 adds real checks to it.
  </action>

echo "flake OK"
