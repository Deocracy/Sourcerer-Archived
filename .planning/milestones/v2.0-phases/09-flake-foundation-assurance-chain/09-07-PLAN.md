<task type="auto">
  <name>Task 1: Make "builds from the cache without compiling" a standing CI gate</name>
  <files>.github/workflows/ci.yml</files>
  <read_first>
    - .github/workflows/ci.yml (from Plans 04 and 06 — the existing job names and gating this job slots behind)
    - flake.nix (the `nixConfig` substituter block from Plan 06 that a fresh checkout relies on)
    - .planning/phases/09-flake-foundation-assurance-chain/09-VALIDATION.md (the FOUND-01 row and its "Manual-Only Verifications" entry, which this task upgrades from manual to automated)
  </read_first>
  <action>
    Add a `cache-cold-build` job to `.github/workflows/ci.yml` on `ubuntu-latest` with
    `needs: [publish]` and the same push-on-default-branch `if:` guard the publish job uses.

    A GitHub-hosted runner is a genuinely cold machine — a fresh VM with no warm `/nix/store`
    entry for this project's closures. That makes it a better standing proof of FOUND-01 than a
    manual second-machine test on hardware that may have built the closure before.

    Steps: `actions/checkout@v7`; `DeterminateSystems/nix-installer-action@v22`; then
    `nix build .#substrate-system --max-jobs 0 --accept-flake-config -L`.

    `--max-jobs 0` is the entire mechanism: it forbids Nix from running any build locally, so the
    command can only succeed if every path in the closure was substituted. If anything must be
    compiled, the job fails with an explicit "cannot build ... max-jobs is 0" error rather than
    quietly taking twenty minutes and passing. Do not substitute a timing heuristic or a log grep
    for this flag. `--accept-flake-config` is required because the substituter is declared in the
    flake's `nixConfig` and a non-interactive runner cannot answer the trust prompt.

    Add a step after the build that asserts the closure actually came from the Sourcerer cache and
    not solely from `cache.nixos.org` — query the cache for the built output path's `.narinfo` and
    fail if it is absent. Without this, a closure containing only upstream nixpkgs paths would pass
    the cold-build test while proving nothing about the project's own cache.

    Add a comment stating that this job is FOUND-01's standing proof, that removing or weakening
    it silently converts a verified guarantee back into a claim, and that Phase 10 and Phase 11
    both inherit the guarantee this job defends.

    Push to the default branch and confirm the job runs green.
  </action>
  <verify>
    <automated>bash -c '
set -euo pipefail
grep -q "cache-cold-build" .github/workflows/ci.yml
grep -q -- "--max-jobs 0" .github/workflows/ci.yml
grep -q -- "--accept-flake-config" .github/workflows/ci.yml
grep -qE "needs:.*publish" .github/workflows/ci.yml
gh run list --limit 1 --json conclusion --jq ".[0].conclusion" | grep -q success
gh run view --json jobs --jq "[.jobs[] | select(.name | test(\"cache-cold-build\")) | .conclusion]" | tee /dev/stderr | grep -q success
echo "cold-build gate OK"
'</automated>
  </verify>
  <acceptance_criteria>

    - Its build step passes `--max-jobs 0` and `--accept-flake-config`.

    - The latest default-branch run shows `cache-cold-build` with conclusion `success` — meaning a cold runner assembled the substrate closure with zero local compilation.
    - The job carries a comment identifying it as FOUND-01's standing proof.

  <files>docs/CACHE-RUNBOOK.md</files>

  <action>
    Demonstrate FOUND-02 by making CI genuinely red on purpose, on a throwaway branch — never on
    the default branch, since the publish job is gated to the default branch and a red default
    branch is a real outage for anything already consuming the cache.

    Procedure:
    1. Create a branch. Introduce one deliberate, obviously-temporary failure. Prefer breaking the
       seed nixosTest's assertion (change the expected response marker to a value the placeholder
       service does not serve) — that exercises the most valuable and most fragile leg of the
       chain, rather than a trivially-broken YAML file that might fail before any job starts.
    2. Push the branch and open a pull request so the workflow runs.
    3. Record: `nix-checks` fails; the `publish` job's status is `skipped`, not `failure` — an
       unmet `needs:` never starts the job, which is what "blocks publish" means mechanically.
       Confirm via `gh run view --json jobs` rather than by eye.
    4. Confirm nothing new landed in the cache: query the cache for the branch build's would-be
       output path and confirm it is absent.
    5. Run the same experiment a second way to cover the other check leg: on the same branch,
       restore the nixosTest and instead break the drift gate (set `rust-toolchain.toml`'s channel
       to a version the Windows job will not resolve to). Confirm `windows-tauri` goes red and
       `publish` is again `skipped`. Testing both legs matters because they fail through different
       mechanisms and only one of them was ever exercised locally.
    6. Delete the branch and close the PR. Verify the default branch is untouched:
       `git diff` against it must be empty for every file the experiment altered.

    Then add an `## Evidence` section to `docs/CACHE-RUNBOOK.md` recording, with run URLs and
    dates: the green end-to-end run (all four jobs), the cold-build proof from Task 1 including
    the `--max-jobs 0` invocation, and both red-blocks-publish experiments with the specific job
    conclusions observed (`failure` for the check job, `skipped` for publish). Cite URLs, not
    prose summaries — a claim with a run URL survives; a claim without one decays into folklore
    within two phases.

    Also update the Red-channel-response section Plan 06 wrote if this experiment revealed
    anything it got wrong, such as a failure mode that produces a confusing error message.
  </action>
